# 代码复核规则

本文件同时约束派发方（主智能体）与复核方（子智能体）。规则不绑定具体源码位置，按本次实现涉及的能力与风险选择条目。

## 一、派发复核（主智能体）

### 1. 时机与主体

实现完成、验证通过之后，汇报之前。复核不得由实现者本人或同一上下文完成，必须交给独立子智能体。

### 2. 派发提示词

派发提示词先声明双方角色，再给材料。开头必须写明类似内容：

> 你是负责复核代码的子智能体。你的任务是按 `rule/review.md` 复核本次改动，只输出发现与证据，不修改源码。

随后给出：

- 原始需求与验收点，保留原文，不改写成结论；
- 明确不做的部分与已知约束；
- 改动文件清单与最终 diff，或可复现 diff 的命令；
- 已执行的验证命令与结果；
- 相关调用方与上下游的位置，只给定位，不给判断。

要求复核者直接读文件与调用链。只依据派发摘要下结论的复核无效。

### 3. 复核者约束

只读：不修改源码、不执行 git 写操作、不新增依赖。可运行类型检查、测试等验证命令。发现问题只报告，不顺手修复。

### 4. 处理报告

- 先判定范围，再决定动作：该发现是否改变原需求行为？是否属于本次方案范围？
- 不改变原需求行为、且属于本轮范围的问题：直接修复，修完重新验证。
- 需要变更原需求行为的问题：不得直接修改。原需求行为包括用户可见语义、交互流程、接口契约、错误语义、配置默认值与既有数据含义。整理为“问题—证据—可选方案—影响面”上报用户，由用户决定。
- 超出本次方案范围的发现：不得直接修改，也不顺手重构。整理后上报用户，注明建议处理时机。
- 修复改变了行为或触及新路径：再派一次增量复核，范围限定为修复 diff。
- 对报告有异议：用代码与可复现路径核对，不以“我认为”驳回。

## 二、复核程序（子智能体）

### 1. 复述意图

用自己的话写清：本次要解决的问题、验收点、明确不做的部分。与需求或对话不一致时先指出，不要用复核掩盖理解偏差。

### 2. 重读最终 diff

- 从最终文件重读，不凭记忆或派发摘要。
- 对每个改动点回答：谁调用它、失败时谁感知、删除它会破坏什么。
- 找出 diff 之外被牵动但未改的地方：调用方、测试、类型、配置、文档。

### 3. 追踪关键路径

对正常、失败、取消或超时、边界输入四条路径，沿实际调用链走一遍，而不是停在单个函数。重点确认失败分支是否真的被处理，而不是只被捕获；返回值与错误是否被上游使用。

### 4. 按领域逐项检查

只检查本次实现涉及的领域；未涉及的写“未涉及”，不硬凑。

#### 资源与生命周期

适用于创建了需要显式释放的东西：连接、客户端、文件句柄、监听器、订阅、定时器、后台任务、缓存条目、临时目录、锁。

- 每个获取点是否都有对应释放点？正常、异常、取消、超时四条路径都释放吗？
- 释放是否集中在一个幂等出口？重复调用是否安全？部分初始化失败时能否安全清理？
- 所有权是否明确？跨层传递时，持有人销毁时被持有者是否跟着销毁？
- 上层取消、超时或断开是否传到下层？下层是否真的停止工作，而不只是标记？
- 后台任务是否有终止条件？失败是否至少被记录？作用域结束时是否被等待或取消？
- 缓存与注册表的条目何时移除？是否存在只增不减的集合？
- 关闭顺序是否与创建顺序相反（如需要）？释放是否依赖其他资源仍存活？

#### 并发与共享状态

适用于异步流程、共享可变状态、领取或租约、重试、唤醒、队列、缓存失效、多消费者。

- 读—判断—写是否被原子保护？两个请求同时到达时，会不会都通过检查？
- await 前后状态是否可能变化？检查与使用之间是否有空隙？
- 重复执行、重试、重复投递是否产生重复副作用？收尾或结算是否可重复调用？
- 合法状态迁移是否被约束？是否存在“结束”之后仍能写入或再次启动的路径？
- 等待方在检查与挂起之间到达的事件会不会丢？通知是否在状态更新之后发出？
- 并发完成顺序是否影响结果？需要有序的地方是否真的有序？
- 异常时锁、标记、占位是否释放？崩溃后残留状态如何恢复或被识别？
- 等待链是否有环？重试是否可能无限循环？

#### 测试

适用于新增或修改测试、测试替身、断言，或实现改变了可观察行为。

- 断言是否落在对外可观察结果上？只重构内部实现时，测试是否仍应成立？
- 成功、错误、取消或超时、边界输入是否至少各有一条？
- 是否依赖时间、顺序、随机、网络或全局状态？失败能否稳定复现？
- 测试之间是否共享状态？执行顺序变化是否影响结果？
- 是否只断言“不抛错”或对象存在？关键字段与副作用是否被验证？
- 测试替身是否只替代外部依赖？替身与真实实现不一致时是否会产生假通过？
- 本次行为变化是否让已有测试失去意义或变成假通过？删除或修改测试是否有明确理由？
- 如果实现回退到修改前，测试是否会失败？

#### 契约与兼容

适用于改动对外接口、返回结构、错误语义、配置项、状态机、消息格式、默认值。

- 所有调用方是否已同步？是否存在仍按旧语义调用的地方？
- 校验是否放在系统边界？内部调用是否被误当作“不需要校验”的理由？
- 错误类型与信息是否足以区分可恢复与不可恢复？内部异常是否被原样透出？
- 同一接口在不同分支是否返回同构结果？空值、缺省与错误是否被混淆？
- 新增或修改的配置是否有真实使用者？默认值是否改变既有行为？非法值如何处理？
- 状态与允许的迁移是否显式？是否新增了不可达或无法退出的状态？
- 已有数据、消息、调用方是否需要迁移？不做兼容时是否说明影响面？
- 契约变化是否同步到类型、注释与文档？

#### 安全与外部输入

适用于接收外部输入、鉴权或授权、敏感数据、拼接命令或查询、反序列化、文件与路径处理、网络暴露。

- 哪些数据来自外部？进入内部前是否校验或规范化？
- 查询、命令、模板、日志是否参数化或转义？是否有字符串拼接进入执行路径？
- 每个入口是否校验身份？是否校验“能否操作这个对象”，而不只是“是否已登录”？
- 客户端可控字段能否改写服务端决定的值，如归属、层级、状态？
- 密钥、令牌、个人信息是否进入日志、错误信息、响应或仓库？
- 用户提供的路径是否被限制在预期目录？是否存在穿越或覆盖？
- 不可信输入是否被当作可信结构使用？解析失败是否安全失败？
- 外部输入能否导致内存、连接或任务无界增长？是否有上限？
- 失败时是拒绝还是放行？调试开关是否可能在生产打开？

#### 数据与持久化

适用于写入或读取持久化数据、事件、日志、缓存，且顺序、幂等、一致性重要。

- 写入顺序是否被保证？并发写入是否会重号或覆盖？编号与键的生成是否单飞？
- 一次逻辑操作涉及多次写入时，中途失败会留下什么状态？是否需要事务？
- 重试或重复提交是否产生重复记录？去重键是否可靠？
- 并发修改是否丢失更新？是否需要版本号或条件更新？
- 缓存写入与失效，和数据源更新的顺序是否正确？失败时缓存是否会长期错误？
- 写入失败时内存状态是否与持久化状态分叉？后续读取以谁为准？
- 分页、过滤、排序是否稳定？空结果与错误是否区分？
- 结构或语义变化是否需要数据迁移？旧数据读取是否仍正确？
- 是否写入了不应持久化的数据？单条记录是否有无界增长风险？

### 5. 证据门槛

每条发现必须包含：

- 触发条件：什么输入、时序或状态会走到；
- 具体位置：哪个文件、哪个分支或语句；
- 后果：错误结果、泄漏、数据不一致、契约破坏等；
- 为何现有代码挡不住。

达不到以上四项的，降级为“待确认”或不写。

每条发现同时标注两项，供派发方分流：

- 范围：本次方案内 / 超出本次方案；
- 行为：不改变原需求行为 / 需要变更原需求行为。

### 6. 输出

- 结论：通过 / 有风险 / 未验证。
- 发现列表按严重级别排序，每条给出证据、修复建议、范围与行为标注。
- 对需要变更原需求行为或超出方案范围的发现，单列一节，写清为什么不能就地修复。
- 明确写出未验证的部分及原因。
- 不写“整体看起来没问题”这类无信息量结论。

## 三、严重级别

- 阻断：会产生错误结果、数据损坏、泄漏、越权，或使主路径不可用。
- 重要：边界或失败路径缺失处理，条件满足时出错。
- 建议：可读性、结构、重复，不影响当前行为。

## 四、常见误报来源

- 只看了新增代码，没看调用方。
- 把框架保证当成需要防御的场景，或把需要防御的场景当成框架保证。
- 用“测试通过”代替“行为正确”。
- 把猜测写成事实。
- 报告没有真实入口的链路，或为不存在的使用场景设计防护。
